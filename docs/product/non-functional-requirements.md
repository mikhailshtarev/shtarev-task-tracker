# Нефункциональные требования к таск-трекеру

## 1. Архитектура и технологический стек

### 1.1. Общая архитектура

Система строится по микросервисной архитектуре с REST API для клиент-серверного взаимодействия и Webhook для асинхронных событий.

Проектируемые сервисы:

| Сервис | Назначение |
| --- | --- |
| Gateway | API-шлюз: маршрутизация, проверка access JWT для не-auth сервисов, выпуск внутреннего контекста, rate limiting, CORS, логирование |
| Auth | Аутентификация и авторизация пользователей |
| Tasks | Управление ветками, планами, задачами, входящими, привычками |
| Notes | Заметки и папки |
| Diary | Личный дневник и медиафайлы |
| Game | Игровой режим, профиль, навыки, достижения, валюта |
| AI | ИИ-анализ задач, привычек, распределение опыта по навыкам |
| Queue | Оркестрация очередей Kafka и webhook-уведомления |

### 1.2. Технологический стек

| Компонент | Технология | Обоснование |
| --- | --- | --- |
| Frontend | React + TypeScript | Устойчивая экосистема, типобезопасность |
| Backend | Java + Spring Boot | Микросервисная архитектура, enterprise-уровень |
| База данных | PostgreSQL | Реляционные данные, транзакции, ACID |
| Хранение файлов | S3-совместимое хранилище | Масштабируемость, стандарт индустрии |
| API-шлюз | Spring Cloud Gateway | Маршрутизация, проверка access JWT для не-auth сервисов, rate limiting |
| Очередь сообщений | Apache Kafka | Высокая пропускная способность, durability, scalability |
| Кэш | Redis | Сессии, кэширование данных |

### 1.3. Развёртывание

- Целевое окружение — веб-приложение в браузере.
- Вертикальное масштабирование: сервер рассчитан на 1 000 пользователей, каждый с до 300 задач и привычек.
- Горизонтальное масштабирование (задел): возможность запуска нескольких инстансов за API-шлюзом.
- Мониторинг: логирование всех операций, метрики производительности, алертинг при превышении лимитов.

## 2. Аутентификация и авторизация

### 2.1. Схема аутентификации

Аутентификация строится на JWT-токенах с refresh-механизмом.

| Параметр | Значение |
| --- | --- |
| Формат токена | JWT (JSON Web Token) |
| Алгоритм подписи | RS256 (асимметричное шифрование) |
| Срок доступа (access token) | 15 минут |
| Срок обновления (refresh token) | 7 дней |
| Хранение refresh token | HTTP-only, Secure cookie (не доступно JS) |
| Хранение access token | В памяти frontend (не в localStorage) |
| Повторное использование токенов | Запрещено (single-use refresh) |

### 2.2. Способы регистрации и входа

Пользователь может зарегистрироваться и войти двумя способами:

| Способ | Описание |
| --- | --- |
| Email + пароль | Регистрация с подтверждением email, вход по паролю |
| Google OAuth 2.0 | Вход через Google аккаунт, автоматическая подгрузка email и имени |

При входе через Google credentials подтягиваются автоматически. Если аккаунт не существует — создаётся новый. Если существует — выполняется авторизация.

### 2.3. Безопасность паролей

| Параметр | Значение |
| --- | --- |
| Алгоритм хеширования | Argon2id (рекомендуемый стандарт OWASP) |
| Стоимость | timeCost = 2, memoryCost = 65536, parallelism = 1 |
| Минимальная длина пароля | 8 символов |
| Требования к сложности | Минимум одна буква в верхнем регистре, одна в нижнем, одна цифра |
| Блокировка после неудачных попыток | 5 попыток → блокировка на 15 минут |
| История последних паролей | Нельзя использовать последние 5 паролей |

### 2.4. Авторизация

- Каждый пользователь работает с собственными данными.
- Доступ к данным другого пользователя запрещён (вертикальный сепаратор).
- Access JWT содержит `user_id` в `sub`. На защищённых маршрутах `auth` сам разбирает и проверяет пользовательский access JWT; Gateway передаёт его без повторной проверки. Для всех остальных защищённых публичных API JWT проверяет Gateway, а целевой сервис получает только минимальный подписанный контекст с `userId` без исходного токена. Ролевая модель в первой версии отсутствует — один пользователь работает только со своими данными; задел на роли — в последующих версиях.
- Не-auth сервис проверяет подлинность внутреннего контекста и права доступа к своему ресурсу; `auth` проверяет собственные токены и права на профиль. Публичные операции входа и обновления сессии используют отдельные правила, refresh JWT из cookie проверяет `auth`.

### 2.5. Защита от атак

| Угроза | Мера защиты |
| --- | --- |
| XSS (межсайтовый скриптинг) | Content-Security-Policy, HTTP-only cookies, экранирование ввода |
| CSRF (межсайтовая подделка запроса) | SameSite=Strict cookie, CSRF-token для state-changing запросов |
| Brute-force | Rate limiting, блокировка после 5 неудачных попыток |
| Token theft | Short-lived access token (15 мин), secure cookie для refresh |
| SQL injection | Parameterized queries, ORM-слои |
| Data breach | Шифрование данных в покое (AES-256), шифрование в передаче (TLS 1.3) |

## 3. Производительность

### 3.1. Целевые показатели

Расчётная нагрузка: 1 000 пользователей × 300 задач/привычек = 300 000 единиц в системе.

| Метрика | Целевое значение | Комментарий |
| --- | --- | --- |
| Время отклика API (основные операции) | ≤ 200 мс | Создание, чтение, обновление задач и привычек |
| Время отклика API (сложные запросы) | ≤ 500 мс | Канбан-доска со всеми ветками, поиск |
| Время отклика API (ИИ-запросы) | ≤ 30 секунд | Асинхронная обработка, пользователь не блокируется |
| Время загрузки главной страницы | ≤ 2 секунды | При стабильном интернет-соединении |
| Время загрузки канбан-доски | ≤ 1 секунда | До 300 задач/привычек в одном запросе |
| Параллельных пользователей (пик) | 100 | Одновременная активность |
| Запросов в секунду (RPS) | ≤ 50 | В пиковые моменты |

### 3.2. Оптимизация запросов к БД

- Индексирование всех внешних ключей и часто фильтруемых полей (статус, приоритет, дата, ветка, тип).
- Пагинация для списков с более чем 50 записей.
- Избегание N+1 запросов: использование JOIN и batch loading.
- Кэширование часто читаемых, редко меняющихся данных применяется при подтверждённой замерами необходимости и с описанной стратегией инвалидации. Настройки пользователя кэшируются в Redis по контракту F-3. Для веток F-4 сначала используются индекс PostgreSQL и keyset-пагинация; Redis-кэш добавляется только при выявленном узком месте.

### 3.3. Масштабирование

- Вертикальное масштабирование: увеличение CPU/RAM сервера.
- Горизонтальное масштабирование (задел): возможность запуска нескольких инстансов за API-шлюзом.
- Базы данных: репликация read-replica при росте нагрузки.

## 4. Надёжность и отказоустойчивость

### 4.1. Доступность

| Метрика | Целевое значение |
| --- | --- |
| Время работы (uptime) | 99,5 % |
| Допустимое время простоя в месяц | ≤ 3,6 часа |
| Восстановление после сбоя | ≤ 15 минут |

### 4.2. Обработка ошибок

| Компонент | Стратегия |
| --- | --- |
| REST API | Retry с exponential backoff (до 3 попыток) для idempotent запросов |
| Kafka-очередь | До 5 попыток (см. бизнес-требования), затем расчёт по умолчанию |
| S3-хранилище | Автоматический failover на другой регион/бакет |
| База данных | Ежесуточное резервное копирование, точка восстановления — 24 часа |

### 4.3. Транзакционность

- Операции архивирования/восстановления выполняются в транзакции.
- При ошибке части операции — откат всей транзакции.
- Итоговые начисления опыта и валюты гарантированы: если задача завершена, начисления происходят даже при ошибке ИИ (расчёт по умолчанию).

## 5. Безопасность данных

### 5.1. Шифрование

| Тип | Алгоритм | Применение |
| --- | --- | --- |
| В передаче | TLS 1.3 | Все HTTP-запросы, подключение к БД, S3, Kafka |
| В покое (БД) | AES-256 | Персональные данные, пароли, токены |
| В покое (S3) | AES-256 | Медиафайлы дневника |

### 5.2. Персональные данные

- Данные пользователя не передаются третьим лицам.
- Google OAuth данные (email, имя) используются только для идентификации.
- Пользователь может запросить экспорт всех своих данных.
- Пользователь может запросить удаление всех своих данных (полная анонимизация).

### 5.3. Логирование и аудит

| Событие | Логгируется |
| --- | --- |
| Регистрация / вход / выход | Да |
| Изменение пароля | Да |
| Создание / архивирование / восстановление сущностей | Да |
| Покупка подписки / переход тарифа | Да |
| Ошибки авторизации | Да |
| ИИ-запросы и ответы | Да (без сохранения содержимого промта) |

Логи хранятся 90 дней. Не содержат паролей, токенов и полных номеров карт.

## 6. Хранение файлов

### 6.1. S3-хранилище

| Параметр | Значение |
| --- | --- |
| Хранилище | S3-совместимое (MinIO для self-hosted, AWS S3 для облака) |
| Шифрование | AES-256 при хранении, TLS при передаче |
| Публичный доступ | Запрещён (приватные бакеты, presigned URLs для доступа) |
| Life-cycle политика | Архивные файлы (> 1 года) → cold storage |

### 6.2. Медиафайлы дневника

| Параметр | Значение |
| --- | --- |
| Макс. размер фото | 10 МБ |
| Макс. размер видео | 100 МБ |
| Поддерживаемые фото | JPEG, JPG, PNG, HEIC, WebP |
| Поддерживаемые видео | MP4, MOV |
| Конвертация HEIC | Автоматическая конвертация в JPEG на бэкенде |
| Сжатие при превышении лимита | Автоматическое (уменьшение разрешения и качества) |
| Дедупликация | SHA-256 хеш: одинаковые файлы не хранятся дважды |

### 6.3. Управление дисковым пространством

- Лимит хранения на пользователя: 3 ГБ.
- При достижении 80 % — уведомление пользователя о необходимости расширения.
- При достижении 100 % — запрет на новые загрузки, старые файлы доступны для чтения.

#### 6.3.1. Покупка дополнительного хранилища

Пользователь может докупить дополнительное хранилище:

| Пакет | Объём | Цена |
| --- | --- | --- |
| Базовый | 3 ГБ (включено) | 0 ₽ |
| Стандарт | +10 ГБ | 99 ₽ |
| Профи | +50 ГБ | 299 ₽ |
| Макс | +100 ГБ | 499 ₽ |

Дополнительное хранилище привязано к подписке и сохраняется даже при переходе на бесплатный тариф (но новые загрузки блокируются при достижении лимита базового пакета).

## 9. Операционный день и тайминги

### 9.1. Операционный день

| Параметр | Значение |
| --- | --- |
| Начало | 04:00 МСК |
| Конец | 04:00 МСК (следующего дня) |
| Часовой пояс | Жёстко привязан к МСК (Europe/Moscow, UTC+3) |
| Независимость от часового пояса пользователя | Да — операционный день всегда по МСК |

### 9.2. Поведение статуса «Ожидает»

| Событие | Действие системы |
| --- | --- |
| Наступила «дата возврата к задаче» | Задача автоматически становится активной (статус «К выполнению») |
| Одновременно | Пользователь получает оповещение в интерфейсе: «Время вернуться к задаче [название]» |
| Если дата возврата не указана | Задача остаётся в статусе «Ожидает» до ручного изменения пользователем |

### 9.3. ИИ-анализ и расчёты

| Процесс | Когда выполняется | Время выполнения |
| --- | --- | --- |
| Анализ привычек | В 04:00 МСК, при завершении операционного дня | ≤ 30 секунд |
| Распределение опыта по навыкам | При завершении задачи | ≤ 15 секунд |
| Повторные попытки ИИ | При ошибке | До 5 попыток с интервалом |
| Расчёт по умолчанию | После 5 неудачных попыток | Мгновенно |

### 9.4. Kafka-очередь

| Параметр | Значение |
| --- | --- |
| Брокер | Apache Kafka |
| Topic для ИИ-задач | ai.task.skill.distribution |
| Topic для ИИ-привычек | ai.habits.daily.analysis |
| Topic для webhook-уведомлений | webhook.notifications |
| Retention | 7 дней |
| Replication factor | 3 (для production) |
| Partitions | 3–6 (зависит от нагрузки) |
| Обработка ошибок | Dead Letter Topic (DLT) после 5 попыток |

## 10. Микросервис AI

### 10.1. Назначение

Сервис AI отвечает за:
- Распределение опыта по навыкам при завершении задачи.
- ИИ-анализ результатов привычек за операционный день.
- Будущие функции ИИ-анализа (анализ недели, персональный помощник).

### 10.2. Взаимодействие

| Компонент | Механизм | Описание |
| --- | --- | --- |
| Tasks → AI | Kafka topic `ai.task.skill.distribution` | Задача завершена → сообщение с полями задачи |
| Habits → AI | Kafka topic `ai.habits.daily.analysis` | 04:00 МСК → сообщение с результатами дня |
| AI → Game | REST API + Webhook | Результат анализа → распределение опыта |
| AI → Queue (DLT) | Kafka topic `ai.dead.letter` | После 5 неудачных попыток |

### 10.3. SLA

| Параметр | Значение |
| --- | --- |
| Время обработки одного запроса | ≤ 15 секунд (задачи), ≤ 30 секунд (привычки) |
| Процент успешных запросов | ≥ 95 % |
| При ошибке | Retry до 5 раз → DLT → расчёт по умолчанию |
| Масштабирование | Auto-scale по длине очереди |

| Параметр | Значение |
| --- | --- |
| Стратегия | Версия в URL: /api/v1/... |
| Обратная совместимость | Удаляемые поля маркируются как deprecated, удаляются через 2 версии |
| Документация | OpenAPI/Swagger-спецификация |

### 15.2. Форматы ошибок API

Единый формат для всех ошибок:

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Задача не найдена",
    "details": null
  }
}
```

| HTTP-код | Когда используется |
| --- | --- |
| 200 | Успешный GET-запрос |
| 201 | Успешное создание ресурса |
| 400 | Неверный формат запроса, валидация |
| 401 | Невалидный или просроченный токен |
| 403 | Нет прав доступа к ресурсу |
| 404 | Ресурс не найден |
| 409 | Конфликт (дублирование, бизнес-правило) |
| 429 | Превышен rate limit |
| 500 | Внутренняя ошибка сервера |

## 17. Distributed Tracing

### 17.1. Инструментарий

| Инструмент | Назначение |
| --- | --- |
| OpenTelemetry | Instrumentation всех сервисов (frontend + backend) |
| Jaeger | Сбор и визуализация трейсов |
| Zipkin | Альтернативный collector (задел на будущее) |

### 17.2. Correlation ID

| Параметр | Значение |
| --- | --- |
| Формат | UUID v4 (36 символов) |
| Передача | Заголовок X-Correlation-ID в HTTP, Kafka-header в сообщениях |
| Логирование | Каждый лог содержит correlation_id |
| Охват | Frontend → Gateway → Backend-сервисы → БД → Kafka → S3 |

### 17.3. Instrumentation

| Компонент | Что трейсится |
| --- | --- |
| Frontend | Время загрузки страниц, HTTP-запросы, ошибки рендеринга |
| Gateway | Маршрутизация, rate limiting, CORS |
| Backend-сервисы | Время обработки запроса, вызовы БД, Kafka, S3 |
| Kafka | Время чтения/записи сообщения, обработка consumer |
| Внешние вызовы | Google OAuth, платёжный шлюз, ИИ-сервис |

### 17.4. Правила трейсинга

- Каждый входящий HTTP-запрос создаёт новый span.
- Корреляция HTTP → Kafka через propagation headers.
- Span tags: http.method, http.url, db.statement, kafka.topic, error.
- Sample rate: 100 % в dev, 10 % в prod (с возможностью увеличения при инциденте).
- PII не логируется (пароли, токены, персональные данные).

## 18. Push-уведомления

### 18.1. Общие положения

Push-уведомления позволяют пользователю получать оповещения о событиях даже когда приложение закрыто.

| Параметр | Значение |
| --- | --- |
| Технология | Web Push API (Browser-native) |
| Провайдер | Firebase Cloud Messaging (FCM) |
| Поддерживаемые браузеры | Chrome 42+, Firefox 44+, Safari 16+, Edge 79+ |
| Офлайн-режим | Уведомления кэшируются и доставляются при восстановлении соединения |

### 18.2. Типы уведомлений

| Тип | Триггер | Пример текста | Когда |
| --- | --- | --- | --- |
| Дата возврата | Наступила дата возврата к задаче в статусе «Ожидает» | «Время вернуться к задаче [название]» | В 04:00 МСК или при наступлении даты |
| Статус задачи | Задача перемещена в «Готово» | «Задача [название] завершена. +X опыта» | При завершении задачи |
| ИИ-анализ завершён | ИИ-анализ привычек обработан | «Результаты дня: +X опыта, +Y навыков» | После завершения ИИ-анализа |
| Подписка | Изменение статуса подписки | «Подписка продлена до [дата]» | При успешной оплате / окончании |

### 18.3. Механика подписки

| Шаг | Описание |
| --- | --- |
| 1 | Пользователь разрешает уведомления в браузере (browser permission prompt) |
| 2 | Frontend получает PushSubscription (endpoint, keys) |
| 3 | Frontend отправляет subscription в backend (POST /api/v1/notifications/push) |
| 4 | Backend сохраняет subscription в БД, привязанную к user_id |
| 5 | Backend отправляет тестовое уведомление для проверки |

### 18.4. Отправка уведомлений

| Компонент | Механизм |
| --- | --- |
| Триггер | Kafka topic `push.notifications` или прямой вызов через Webhook-сервис |
| Провайдер | Firebase Admin SDK |
| Retry | До 3 попыток с интервалом 1 мин, 5 мин, 15 мин |
| Rate limit | 100 уведомлений в минуту на пользователя |
| Дедупликация | Не более 1 уведомления на сущность в час (задача, привычка) |

### 18.5. Управление уведомлениями

| Действие | Описание |
| --- | --- |
| Включить/выключить | Пользователь может отключить каждый тип уведомлений в настройках |
| Отписаться | Полный отказ от push-уведомлений (удаление subscription) |
| Тихие часы | С 22:00 до 08:00 — только критические уведомления (дата возврата) |

### 18.6. Ограничения

- Push-уведомления не в MVP. Реализуется после базовой версии.
- Требуется HTTPS для работы Web Push API.
- Уведомления не являются основным каналом связи — пользователь может отписаться.
- Не заменяют внутренние оповещения в интерфейсе (раздел 9.2 — статус «Ожидает»).
