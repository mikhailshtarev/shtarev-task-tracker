# F-4. Ветки — системное описание

## 1. Архитектура

Фича реализуется в сервисе `tasks`. В F-4 Gateway получает маршрут `/api/v1/branches/**` к `tasks`; текущий маршрут `/api/v1/tasks/**` не покрывает ветки. По [общему контракту аутентификации](../../technical/gateway-access-auth.md) Gateway проверяет пользовательский access JWT на защищённых маршрутах к `tasks` и другим не-auth сервисам. `auth` самостоятельно проверяет JWT на своих защищённых маршрутах. После проверки Gateway передаёт `tasks` только `sub` как `userId` в подписанном внутреннем контексте. Сырой access token, email и остальные claims в `tasks` не передаются; `userId` из публичных URL и тела запроса не принимается.

```text
Frontend ── Bearer access JWT ──▶ Gateway ── подписанный userId ──▶ Tasks service
                                │                                  └── PostgreSQL
                                └── JWKS auth                          ├── branches
                                                                       └── audit_events
```

F-4 использует PostgreSQL и JWT-инфраструктуру F-1/F-2. База `tasks` отделена от базы `auth`, поэтому `branches.user_id` не имеет внешнего ключа на `auth.users`. Интеграций с ИИ, Kafka, файлами или оплатой нет.

### 1.1. Доверенный контекст Gateway → tasks

На `/api/v1/branches/**` применяется единый протокол из [раздела 3 общего контракта](../../technical/gateway-access-auth.md): Gateway удаляет клиентские внутренние заголовки и пользовательский `Authorization`, подписывает `userId` из проверенного `sub` для получателя `tasks`; маршрут F-4 не переписывает путь. `tasks` проверяет подпись, время, метод и путь до контроллера, затем использует только проверенный UUID владельца. Неподлинный контекст даёт внутренний `401 UNAUTHORIZED`; после успешной проверки JWT Gateway преобразует такой ответ `tasks` в публичный `502 UPSTREAM_UNAVAILABLE`. Прямой публичный доступ к `tasks` запрещён. CORS preflight Gateway обрабатывает до проверки JWT и без вызова `tasks`.

То же правило действует для `/api/v1/tasks/**` и остальных не-auth сервисов. На маршрутах `auth` Gateway сохраняет Bearer, и `auth` сам проверяет access JWT. Для будущего получения настроек существует два варианта, которые нужно выбрать в F-6: Gateway выборочно получает их из `auth` и подписанно передаёт `tasks` для HTTP-операции либо `tasks` вызывает `auth` по отдельному сервисному контракту; фоновые операции без Gateway требуют второго варианта.

## 2. Модель данных

Первая миграция сервиса `tasks`, `V1__create_branches.sql`, создаёт таблицы `branches` и `audit_events`. Применённые миграции впоследствии не редактируются.

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `id` | UUID | Первичный ключ |
| `user_id` | UUID | Не null, индекс; идентификатор владельца из проверенного внутреннего контекста |
| `name` | VARCHAR(100) | Не null; сервер валидирует 2–100 кодовых точек Unicode после нормализации из раздела 4 |
| `archived_at` | TIMESTAMPTZ | Null для активной ветки |
| `created_at` | TIMESTAMPTZ | Не null |
| `updated_at` | TIMESTAMPTZ | Не null |

Частичный B-tree индекс `(user_id, created_at DESC, id DESC) WHERE archived_at IS NULL` поддерживает выборку и keyset-пагинацию активных веток. Мягкое удаление реализуется заполнением `archived_at`; физическое удаление запрещено. UUID ветки создаёт приложение; `created_at` и `updated_at` задаются сервером в UTC.

`audit_events` — техническая история изменений пользовательских сущностей сервиса `tasks`, пригодная для F-9. Для F-4 она содержит `id UUID`, `user_id UUID`, `entity_type VARCHAR(32)` (`branch`), `entity_id UUID`, `action VARCHAR(32)` (`created`, `renamed`, `archived`), `changes JSONB NOT NULL`, `occurred_at TIMESTAMPTZ NOT NULL` и необязательный `correlation_id VARCHAR(64)`. `changes` хранит только затронутые поля с `from`/`to`; пароли и токены в неё не попадают. Индекс `(user_id, entity_type, entity_id, occurred_at DESC, id DESC)` подготавливает чтение истории в F-9. Запись события и изменение ветки коммитятся в одной транзакции. Повторное архивирование или переименование без изменения нормализованного названия не создаёт событие. При удалении данных пользователя в F-19 история обрабатывается вместе с его данными; 90-дневный срок обычных логов NFR 5.3 не применяется к этой таблице.

F-5 и F-6 добавят внешние ключи на `branches.id`. Каскадное архивирование будет выполняться сервисным слоем в одной транзакции, а не SQL `ON DELETE CASCADE`, поскольку записи должны сохраняться.

## 3. API-контракты

Машиночитаемый публичный контракт запросов, ответов и ошибок — [openapi.yaml](openapi.yaml). Клиент обращается через Gateway с Bearer access token; внутренние заголовки из раздела 1.1 не являются частью публичного API. Единый формат ошибок: `{ "error": { "code", "message", "details" } }`. Неизвестная или чужая ветка с корректным UUID возвращает `404 NOT_FOUND`; некорректный UUID — `400 VALIDATION_ERROR`. Публичный `401` означает недействительный или отсутствующий access JWT; ошибка доверенного контекста после его проверки возвращается как `502 UPSTREAM_UNAVAILABLE`, поэтому не инициирует обновление токена на клиенте.

### 3.1. `GET /api/v1/branches`

Возвращает активные ветки текущего пользователя, отсортированные по `createdAt` и `id` по убыванию: новые ветки видны первыми. Поддерживает `limit` (целое 1–50, по умолчанию 50), `cursor` и необязательный `q` (поиск по части названия без учёта регистра, 0–100 кодовых точек после нормализации из раздела 4). Символы `%` и `_` в `q` трактуются как обычный текст, а не шаблон SQL. Пустой после нормализации `q` означает отсутствие фильтра. Неверные `limit`, `cursor` или слишком длинный `q` возвращают `400 VALIDATION_ERROR`.

Пагинация — keyset по `(created_at, id)`: при порядке DESC следующая страница выбирает записи с ключом строго меньше последнего элемента предыдущей, с тем же фильтром `q`. Сервис читает `limit + 1` записей и возвращает `nextCursor` только при наличии следующей страницы. Курсор — непрозрачная для клиента Base64URL-кодировка версии формата, `createdAt`, `id` и SHA-256 от UTF-8 байтов нормализованного `q` с сохранением регистра; для отсутствующего или пустого `q` хешируется пустая строка. Его длина ограничена 512 символами. Хеш позволяет не помещать пользовательский текст в курсор и сохранять его размер постоянным. Сервер строго валидирует структуру и соответствие текущему `q` (включая регистр), затем всё равно применяет фильтр владельца. Курсор не является средством авторизации. Новые записи, появившиеся перед текущим курсором, становятся видны после обновления списка с первой страницы.

```json
{
  "items": [
    {
      "id": "8f20d971-bdd8-4d2b-82ea-5fd4e126532f",
      "name": "Спорт",
      "createdAt": "2026-09-16T10:00:00Z",
      "updatedAt": "2026-09-16T10:00:00Z"
    }
  ],
  "nextCursor": null
}
```

### 3.2. `POST /api/v1/branches`

Создаёт ветку текущего пользователя.

```json
{ "name": "Спорт" }
```

Ответ: `201 Created` с объектом ветки и заголовком `Location: /api/v1/branches/{branchId}`. Название нормализуется до сохранения; неверное название возвращает `400 VALIDATION_ERROR`. Одинаковые названия разрешены.

### 3.3. `GET /api/v1/branches/{branchId}`

Возвращает активную ветку текущего пользователя. Для отсутствующей, архивированной или чужой ветки возвращает `404 NOT_FOUND`, чтобы не раскрывать существование чужих данных.

### 3.4. `PUT /api/v1/branches/{branchId}`

Переименовывает активную ветку текущего пользователя.

```json
{ "name": "Здоровье" }
```

Ответ: `200 OK` с актуальным объектом. Если нормализованное имя не изменилось, ответ тот же, но `updated_at` и аудит не меняются. Неверное название — `400 VALIDATION_ERROR`; отсутствующая, архивированная или чужая ветка — `404 NOT_FOUND`.

### 3.5. `POST /api/v1/branches/{branchId}/archive`

Архивирует ветку текущего пользователя. Ответ: `204 No Content`. Повторное архивирование уже архивированной собственной ветки возвращает `204` без изменения `archived_at` и без нового события аудита. Отсутствующая или чужая ветка возвращает `404 NOT_FOUND`.

В F-4 архивируется только запись ветки. После появления планов и задач в F-5/F-6 этот endpoint расширяется каскадной операцией без изменения публичного контракта. Восстановление добавляется F-9.

## 4. Правила обработки

1. Для `name` и `q` используется единый алгоритм: сначала Unicode NFC, затем удаление с обоих краёв только кодовых точек U+0009–U+000D, U+0020, U+00A0, U+1680, U+2000–U+200A, U+2028–U+2029, U+202F, U+205F, U+3000 и U+FEFF. Внутренние пробелы сохраняются. Длина считается в кодовых точках Unicode после этих действий (Java `codePointCount`, JavaScript `Array.from(...).length`), а не в UTF-16 единицах или графемах. Для `name` допустимы 2–100, для `q` — 0–100; пустой `q` равен отсутствующему. Серверная валидация окончательна. Поля JSON вне схемы `BranchInput`, включая `userId`, отклоняются с `400 VALIDATION_ERROR`.
2. Список, чтение и переименование выбирают только `user_id = verifiedUserId AND archived_at IS NULL`. Архивирование сначала ищет запись по `id` и `user_id` независимо от `archived_at`, чтобы отличить повторный вызов своей ветки от чужой или отсутствующей.
3. Создание, переименование и архивирование вместе с соответствующим событием истории выполняются в одной транзакции. Переименование и архивирование сериализуются блокировкой строки ветки, чтобы параллельные запросы не создавали повторных событий и переименование не прошло после архивирования. После F-5/F-6 в эту же транзакцию входит каскадное архивирование дочерних сущностей.
4. Для поиска используется параметризованный запрос с фильтром владельца и экранированным литеральным `q` (`%`, `_` и символ экранирования ищутся буквально). На первом этапе Redis-кэш для пользовательских списков не вводится: индекс и keyset-пагинация дают предсказуемое время выборки без инвалидации на каждое изменение. Необходимость кэша или дополнительного поискового индекса определяется нагрузочными замерами согласно NFR 3.2.

## 5. Безопасность и надёжность

- Gateway отклоняет невалидный JWT и токен с `type != access`. `tasks` отклоняет недоверенный внутренний контекст, самостоятельно валидирует входные данные и проверяет владение `branchId` по проверенному `userId`.
- Ошибки не раскрывают факт существования чужих или архивированных веток.
- Операции записи соответствуют целевому времени основных API до 200 мс (NFR 3.1).
- Архивирование и последующее каскадирование имеют атомарную транзакцию с откатом при ошибке (NFR 4.3).
- Создание, переименование и архивирование записываются в `audit_events` и технические логи согласно NFR 5.3.
