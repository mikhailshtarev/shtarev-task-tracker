# План работ: F-4 Ветки — Backend

## 0. Контекст для агента

Перед началом прочитай в порядке:

1. `AGENTS.md` в корне репозитория.
2. [business-description.md](business-description.md): пользовательские правила и критерии приёмки.
3. [system-description.md](system-description.md) и [openapi.yaml](openapi.yaml): схема данных, контракт API и безопасность.
4. [Общий контракт Gateway-аутентификации](../../technical/gateway-access-auth.md), документы F-2 по JWT и текущую структуру `backend/tasks`, `backend/gateway`.

Работай в `backend/tasks` и `backend/gateway`. Gateway разбирает пользовательский access JWT для `tasks` и остальных не-auth сервисов; `tasks` получает проверенный `userId` из внутреннего контекста. `auth` самостоятельно разбирает access JWT на своих маршрутах — его код в F-4 не меняй. Не меняй публичные API-контракты и не добавляй физическое удаление веток.

Перед этапом 1 проверь доступность PostgreSQL для `tasks`, JWKS сервиса F-2 для Gateway, инъекции HMAC-секрета и приватного TLS-маршрута Gateway → `tasks`. Если окружение F-1/F-2 ещё не подготовлено, веди реализацию и тесты с локальными ресурсами/Testcontainers, но зафиксируй зависимость: сквозную проверку и финальную готовность нельзя отмечать до воспроизводимого окружения. Не заменяй проверку токенов или внутреннего контекста заглушкой.

## 1. Подготовка сервиса и маршрута

- [ ] Добавить в `tasks` только необходимые зависимости: PostgreSQL driver и Spring Data JPA для хранения веток; Flyway для версионирования схемы; Bean Validation для DTO; Spring Boot Test и Testcontainers PostgreSQL для проверок с реальной БД. HMAC-SHA256 реализовать средствами JCA без новой библиотеки. Не подключать OAuth2 Resource Server, Redis и стороннюю библиотеку пагинации.
- [ ] Настроить подключение `tasks` к собственной БД, Flyway и `ddl-auto=validate`; секреты брать из окружения.
- [ ] В Gateway для защищённых маршрутов к `tasks` и остальным не-auth сервисам проверять подпись, `exp`, `nbf` (если есть), `iss`, `type=access` и UUID в `sub`; удалять клиентские `X-Internal-*` и не пересылать пользовательский `Authorization` в `tasks`. Проверка JWT и получение JWKS не должны блокировать WebFlux event loop: использовать реактивный декодер или эквивалентный неблокирующий подход с кэшем ключей и безопасной обработкой неизвестного `kid`. Подписывать минимальный контекст по фактическому пути после переписываний. Для `/api/v1/auth/**` сохранить передачу Bearer без повторной проверки в Gateway; клиентские `X-Internal-*` удалять и там.
- [ ] Обрабатывать CORS preflight в Gateway до фильтра JWT: разрешённый `OPTIONS` с `Origin` и `Access-Control-Request-Method` не требует Bearer, не вызывает `tasks` и не создаёт внутренний контекст.
- [ ] Добавить в Gateway маршрут `/api/v1/branches/**` к `tasks`; существующее поведение маршрутов `auth` не менять.
- [ ] В `tasks` до контроллера проверять HMAC, время и формат `X-Internal-User-Id`; помещать только проверенный UUID в контекст запроса. Отсутствующий или неверный контекст отклонять. Прямой публичный доступ к сервису закрыть на уровне сети.
- [ ] Если после успешной проверки JWT `tasks` возвращает внутренний `401`, преобразовать ответ на Gateway в публичный `502 UPSTREAM_UNAVAILABLE` по OpenAPI; логировать причину и correlation ID без токенов и подписей. `401` от самого Gateway оставить только для проблем с пользовательским JWT.

**Готовность:** запрос к веткам проходит через Gateway; отсутствие, неверный или refresh JWT на маршруте `tasks` отклоняется Gateway. `tasks` не получает пользовательский Bearer и отклоняет запрос без подлинного внутреннего контекста. Маршруты `auth` сохраняют Bearer и собственную проверку JWT.

## 2. Схема данных и история

- [ ] Создать первую миграцию `V1__create_branches.sql` с таблицами `branches` и `audit_events`, ограничениями и индексами из системного описания.
- [ ] Создать entity/repository ветки и компонент записи событий истории. Не предполагать наличия готовой инфраструктуры аудита в `tasks`.
- [ ] Записывать событие `created`, `renamed` или `archived` вместе с изменением ветки в одной транзакции; пустые изменения и повторное архивирование не создают событие.

**Готовность:** Flyway применяет миграцию на чистой БД, Hibernate проверяет схему, запись ветки и событие истории атомарны.

## 3. Сервисный слой

- [ ] Создать `BranchService` со списком, поиском по `q`, созданием, чтением, переименованием и архивированием.
- [ ] Нормализовать `name` и `q` строго по алгоритму NFC и краевого удаления из раздела 4 системного описания; считать кодовые точки, а не UTF-16 единицы. Сервер валидирует `name` 2–100 и `q` 0–100. Одинаковые названия не запрещать.
- [ ] Реализовать keyset-пагинацию по `(created_at DESC, id DESC)` через частичный индекс: фильтр владельца и активного статуса, `limit + 1`, курсор с версией и SHA-256 от UTF-8 байтов нормализованного `q` с сохранением регистра.
- [ ] Для `GET` и `PUT` выбирать только активную собственную ветку. Переименование и архивирование сериализовать блокировкой строки. Для архивации искать собственную ветку независимо от статуса: активную архивировать, уже архивированную вернуть без изменений; чужую или отсутствующую не раскрывать.

**Готовность:** сервис не выдаёт и не изменяет чужие ветки, выдача страниц не дублируется, повторное архивирование идемпотентно.

## 4. REST API и контракт

- [ ] Добавить DTO запросов, ответов и ошибок по `openapi.yaml`.
- [ ] Реализовать пять endpoint'ов с валидацией `branchId`, `name`, `limit`, `cursor` и `q`, включая параметризованный поиск, литеральную трактовку `%` и `_` и отклонение неизвестных полей `BranchInput`, в том числе `userId`.
- [ ] Возвращать `201` с `Location` при создании, `204` при архивировании, `400 VALIDATION_ERROR` для неверного ввода, публичный `401 UNAUTHORIZED` для неверного access token на Gateway, прямой внутренний `401` для неверного контекста в `tasks`, публичный `502 UPSTREAM_UNAVAILABLE` при таком ответе через Gateway, `404 NOT_FOUND` для чужой/отсутствующей ветки.
- [ ] Сверить фактический HTTP-контракт с `openapi.yaml`; при изменении API обновить спецификацию и типы клиента до завершения фичи.

**Готовность:** публичные запросы через Gateway соответствуют OpenAPI, внутренние запросы к `tasks` — протоколу раздела 1.1 системного описания.

## 5. Подготовка каскадного архивирования

- [ ] Оставить архивирование ветки транзакционной точкой расширения для F-5/F-6 без зависимостей от ещё не созданных таблиц.
- [ ] Зафиксировать в тесте F-4 отсутствие физического удаления. Каскадные интеграционные тесты добавить в F-5/F-6, когда появятся дочерние сущности.

**Готовность:** контракт endpoint'а архивации не потребуется менять при добавлении планов и задач.

## 6. Финальная проверка

- [ ] Сверить реализацию с критериями приёмки F-4; отложенный каскадный критерий проверить в F-5/F-6.
- [ ] Выполнить тесты `backend/tasks` и затронутые тесты `backend/gateway`; smoke-проверкой убедиться, что защищённые и публичные маршруты `auth` не изменились. Сквозную проверку с PostgreSQL, JWKS, секретом и приватным TLS-маршрутом завершить на воспроизводимом окружении F-1/F-2.
- [ ] Проверить по плану запроса, что список использует частичный индекс и не выполняет OFFSET; оценить необходимость дополнительных индексов и кэша только по нагрузочным замерам.

**Готовность:** тесты зелёные, публичный контракт совпадает с OpenAPI, доступ через Gateway работает.
