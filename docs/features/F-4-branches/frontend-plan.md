# План работ: F-4 Ветки — Frontend

## 0. Контекст для агента

Перед началом прочитай в порядке:

1. `AGENTS.md` в корне репозитория.
2. [business-description.md](business-description.md): сценарии и критерии приёмки.
3. [system-description.md](system-description.md) и [openapi.yaml](openapi.yaml): API-контракты и ошибки.
4. Документацию авторизации F-2 и существующие `api/client`, `AuthContext`, `ProtectedRoute`, `ErrorDisplay`.

Работай только в `frontend/src`. Все интерфейсные тексты F-4 — на русском и вынесены в один модуль строк без новой библиотеки локализации. Не реализуй планы, задачи, отдельный раздел архива или восстановление — это отдельные фичи. Действие архивирования ветки входит в F-4.

До сквозной проверки убедись, что Gateway направляет `/api/v1/branches/**` в `tasks`, а F-2 выдаёт действующий access token. Верстку и тесты клиента можно выполнять с мокированным API до готовности backend.

## 1. Типы и API-слой

- [ ] Добавить типы `Branch`, `BranchPage`, параметров списка и ошибок по `openapi.yaml`.
- [ ] Добавить в API-слой методы: `getBranches({ limit, cursor, q })`, `createBranch`, `getBranch`, `updateBranch`, `archiveBranch`. Параметры списка кодировать через `URLSearchParams`; использовать существующий `authorizedRequest` с Bearer token и refresh-механизмом.
- [ ] Обрабатывать ошибки API через существующий механизм, без технических деталей для пользователя. `401` от Gateway запускает существующее обновление access JWT; `502 UPSTREAM_UNAVAILABLE` показывает сообщение о временной недоступности и возможность повторить запрос без refresh, очистки сессии и редиректа на вход.

**Готовность:** типы компилируются, запросы используют существующий авторизованный клиент.

Отменять устаревший запрос, чтобы старый результат не перезаписал новый.

**Готовность:** пользователь видит только данные, полученные сервером для своей учётной записи.

## 3. Создание и переименование

- [ ] Реализовать форму создания с NFC, удалением краевых пробелов и подсчётом кодовых точек по разделу 4 системного описания; проверять длину `name` 2–100 и отправлять нормализованное название. Те же правила использовать при переименовании; серверный ответ остаётся окончательным решением при расхождении правил клиента и сервера.
- [ ] После создания сбрасывать текущий поиск и загружать первую страницу: новая ветка должна быть видна сверху даже при наличии более 50 веток. После переименования обновлять карточку или убирать её из результатов, если новое название не совпадает с текущим поиском.
- [ ] Реализовать переименование через компактную форму на странице ветки или в списке.
- [ ] Показывать ошибки валидации у поля, а успешные действия сразу отражать в списке.

**Готовность:** критерии приёмки 1–3 бизнес-описания воспроизводятся без перезагрузки страницы.

## 4. Открытие и архивирование

- [ ] Создать защищённую страницу `/branches/:branchId` с названием и явным пояснением «Планы и задачи пока не добавлены»; задел под их отображение относится к F-5/F-6.
- [ ] Добавить действие «Архивировать» с подтверждением: ветка исчезнет из рабочего списка, данные сохранятся.
- [ ] Подтверждение сделать доступным с клавиатуры: фокус переводится в диалог и возвращается после отмены; кнопки имеют понятные подписи. Повторное нажатие во время запроса не отправляет вторую операцию.
- [ ] После успешного архивирования перенаправлять на `/branches` и показывать подтверждение.
- [ ] Для `404` показывать понятный экран «Ветка не найдена или недоступна».

**Готовность:** архивированная ветка не показывается в обычном списке; пользователь не видит технических деталей ошибки.
