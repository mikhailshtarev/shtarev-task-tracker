# План работ: F-5 Планы работ — Backend

## 0. Контекст для агента

Перед началом прочитай в порядке:

1. `AGENTS.md` в корне репозитория.
2. [business-description.md](business-description.md): бизнес-правила и критерии приёмки.
3. [system-description.md](system-description.md) и [openapi.yaml](openapi.yaml): схема данных, публичный API, архивирование и безопасность.
4. Документацию и реализацию F-4: `branches`, `audit_events`, Gateway → Tasks контекст и правила нормализации; [общий контракт Gateway](../../technical/gateway-access-auth.md).

Работай в `backend/tasks` и `backend/gateway`: новый маршрут `/api/v1/work-plans/**` требует изменения и тестов Gateway; вложенный `/api/v1/branches/{branchId}/plans` уже покрывается маршрутом веток. Механизм JWT и подписанного контекста F-4 не меняй. Не добавляй физическое удаление, восстановление или задачи — это F-9 и F-6. Пустой план разрешён, а будущая задача не обязана иметь план.

## 1. Миграция и модель данных

- [ ] Создать миграцию `V2__create_work_plans.sql` с таблицей, внешним ключом и частичным индексом из системного описания.
- [ ] Создать entity `WorkPlan` и repository для списков активных планов branch с keyset-пагинацией.
- [ ] Переиспользовать таблицу `audit_events` F-4 без новой миграции аудита. Добавить запись событий с `entity_type = work_plan`: существующий `BranchAudit` жёстко использует `branch`, поэтому нужен отдельный небольшой writer или обобщение без изменения формата прежних событий.

**Готовность:** Flyway применяет V1 и V2 на чистой БД; план нельзя создать без существующей ветки.

## 2. Сервисный слой планов

- [ ] Создать `WorkPlanService`: список, создание, чтение, переименование и архивирование.
- [ ] Проверять владельца через активную родительскую ветку и проверенный `userId` из внутреннего контекста. Для создания, переименования и архивирования в одной транзакции сначала блокировать строку ветки и проверить её активность, затем при необходимости строку плана; при обращении по `planId` повторно проверить план после блокировки ветки.
- [ ] Применить точный алгоритм нормализации F-4 (NFC, заданные краевые пробелы, число кодовых точек); валидировать 2–150 для `name` и 0–150 для `q`.
- [ ] Реализовать keyset-пагинацию по `(created_at DESC, id DESC)` с фильтром владельца/активной ветки/активного плана, `limit + 1` и курсором из системного описания, привязанным к `branchId` и нормализованному `q` с сохранением регистра.
- [ ] Записывать события `created`, `renamed`, `archived` с полями `changes` из системного описания в одной транзакции с изменением плана; пустое переименование и повторное архивирование не создают события.

**Готовность:** пользователь видит только активные планы своей активной ветки, а повторные операции без изменения не порождают дубликаты истории.

## 3. Расширение архивирования ветки

- [ ] После блокировки ветки в транзакции архивирования F-4 наборно обновить активные планы по `branch_id` и `archived_at IS NULL`, получить ID фактически изменённых строк (`UPDATE ... RETURNING id` или эквивалент) и записать для каждого одно событие `work_plan/archived`. Для ветки и планов использовать один момент `archived_at`/`updated_at`; не допускать устаревших JPA entity после bulk-обновления.
- [ ] Уже архивированным планам не менять `archived_at`/`updated_at` и не создавать второе событие. Повторное архивирование собственной ветки остаётся `204` без новых событий.
- [ ] При ошибке архивирования или записи любого события откатывать изменение ветки, всех дочерних планов и аудит.

**Готовность:** после архивирования ветки нет активных планов этой ветки; при ошибке ветка и планы остаются активными.

## 4. REST API

- [ ] Добавить DTO запросов и ответов для планов и cursor-страницы по `openapi.yaml`; отклонять неизвестные поля тела, включая `userId` и `branchId`.
- [ ] Реализовать nested `GET/POST /branches/{branchId}/plans` и `GET/PUT/POST archive /work-plans/{planId}`.
- [ ] Вернуть `404 NOT_FOUND` для чужих, архивированных и отсутствующих веток/планов, кроме повторной архивации собственного плана в активной ветке (`204`); `400 VALIDATION_ERROR` для неверных UUID, курсоров и полей. Публичные `401`/`502` сохранить по контракту F-4.
- [ ] Добавить в Gateway маршрут `/api/v1/work-plans,/api/v1/work-plans/**` к `tasks` без переписывания пути; сохранить проверку JWT, удаление Bearer и подписание контекста. Проверить, что вложенный маршрут планов проходит по существующему `/api/v1/branches/**`.

**Готовность:** оба семейства публичных URL проходят через Gateway, ответы и статус-коды соответствуют OpenAPI.

## 5. Финальная проверка

- [ ] Сверить реализацию с критериями приёмки бизнес-описания.
- [ ] Проверить миграции V1/V2, транзакционность и отсутствие N+1 в списках планов.
- [ ] Выполнить тесты `backend/tasks` и затронутые тесты `backend/gateway`; сверить пять endpoint'ов с `openapi.yaml` и проверить регрессию архивирования ветки F-4.

**Готовность:** тесты зелёные; публичные контракты и аудит согласованы с F-4.
