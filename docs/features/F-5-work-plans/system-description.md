# F-5. Планы работ — системное описание

## 1. Архитектура

Фича расширяет сервис `tasks` и использует защищённую доставку контекста пользователя Gateway → Tasks, принятую в F-4. Существующий маршрут `/api/v1/branches/**` покрывает вложенные операции планов; в F-5 Gateway дополнительно маршрутизирует `/api/v1/work-plans/**` в `tasks` без переписывания пути. Для обоих маршрутов Gateway проверяет access JWT и передаёт подписанный внутренний `userId`. Сервис не принимает `userId` из публичного URL или тела запроса. Правила публичных `401` и `502`, а также CORS preflight остаются такими же, как в [общем контракте Gateway](../../technical/gateway-access-auth.md).

```text
Frontend → Gateway → Tasks service → PostgreSQL
                         ├── branches
                         ├── work_plans
                         └── audit_events
```

Интеграций с ИИ, Kafka, файлами и оплатой нет. F-5 зависит от таблиц `branches` и `audit_events`, созданных в F-4. Пустой план допустим; в F-6 задача сможет существовать без плана. Если план у задачи указан, он принадлежит той же ветке.

В F-5.1 активные планы также входят в read-model левого дерева как дочерние узлы веток; публичные CRUD-контракты F-5 остаются источником истины для их страницы.

## 2. Модель данных

Миграция `V2__create_work_plans.sql` создаёт таблицу `work_plans`.

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `id` | UUID | Первичный ключ |
| `branch_id` | UUID | Не null, внешний ключ на `branches.id` |
| `name` | VARCHAR(150) | Не null; сервер валидирует длину 2–150 после нормализации |
| `archived_at` | TIMESTAMPTZ | Null для активного плана |
| `created_at` | TIMESTAMPTZ | Не null, UTC |
| `updated_at` | TIMESTAMPTZ | Не null, UTC |

Индекс `(branch_id, created_at DESC, id DESC) WHERE archived_at IS NULL` обеспечивает выборку активных планов и keyset-пагинацию. Владелец плана определяется соединением с `branches`; дублирование `user_id` в `work_plans` не требуется. UUID и время создания/изменения задаёт сервер в UTC; `updated_at` меняется только при фактическом переименовании или архивировании.

F-6 добавит необязательный внешний ключ задач на `work_plans.id`: отсутствие плана у задачи допустимо. Каскадное архивирование выполняется в сервисном слое в одной транзакции, а не через SQL `ON DELETE CASCADE`, поскольку физическое удаление запрещено.

## 3. API-контракты

Машиночитаемый публичный контракт — [openapi.yaml](openapi.yaml). Все endpoints требуют access JWT на Gateway. Формат ошибок: `{ "error": { "code", "message", "details" } }`. Чужие, архивированные и отсутствующие сущности возвращают `404 NOT_FOUND`; некорректные UUID и данные — `400 VALIDATION_ERROR`. Публичный `401 UNAUTHORIZED` означает проблему с access JWT до вызова `tasks`; отклонение внутреннего контекста в `tasks` даёт прямой внутренний `401`, который Gateway преобразует в публичный `502 UPSTREAM_UNAVAILABLE` по контракту F-4.

### 3.1. `GET /api/v1/branches/{branchId}/plans`

Возвращает активные планы активной ветки текущего пользователя в порядке `createdAt DESC, id DESC`. Поддерживает `limit` от 1 до 50 (по умолчанию 50), непрозрачный `cursor` и `q` — поиск по части названия без учёта регистра, длиной до 150 кодовых точек после нормализации.

```json
{
  "items": [
    {
      "id": "535f5d9e-4533-4896-af28-8a2d129930ec",
      "branchId": "8f20d971-bdd8-4d2b-82ea-5fd4e126532f",
      "name": "Тренировки",
      "createdAt": "2026-09-17T10:00:00Z",
      "updatedAt": "2026-09-17T10:00:00Z"
    }
  ],
  "nextCursor": null
}
```

Пагинация — keyset по `(created_at, id)`: при порядке DESC следующая страница содержит записи с ключом строго меньше последнего элемента текущей. Сервис читает `limit + 1` записей и выдаёт `nextCursor` только при наличии следующей страницы. Курсор — непрозрачная для клиента Base64URL-кодировка без padding UTF-8 строки `v1|<canonical-branchId>|<createdAt>|<planId>|<queryHash>`, где UUID записаны канонически в нижнем регистре, `createdAt` — `Instant.toString()`, а `queryHash` — SHA-256 от UTF-8 байтов нормализованного `q` с сохранением регистра в нижнем hex. Для отсутствующего или пустого после нормализации `q` хешируется пустая строка. Длина курсора — не более 512 символов. Сервер строго проверяет структуру, каноническое кодирование и соответствие текущим `branchId` и `q`; неверный или перенесённый в другую ветку курсор даёт `400 VALIDATION_ERROR`. Курсор не авторизует запрос: проверка владельца и активной ветки выполняется заново. Символы `%`, `_` и символ экранирования в `q` ищутся как обычный текст. Новые планы перед текущим курсором видны после обновления первой страницы.

### 3.2. `POST /api/v1/branches/{branchId}/plans`

Создаёт план в активной ветке текущего пользователя.

```json
{ "name": "Тренировки" }
```

Ответ: `201 Created` с объектом плана и заголовком `Location: /api/v1/work-plans/{planId}`. Нормализованное название сохраняется на сервере; повторяющиеся названия разрешены. Тело содержит только `name`: неизвестные поля, в том числе `userId` и `branchId`, отклоняются с `400 VALIDATION_ERROR`.

### 3.3. `GET /api/v1/work-plans/{planId}`

Возвращает активный план текущего пользователя вместе с `branchId`. Архивированный, отсутствующий или чужой план возвращает `404 NOT_FOUND`.

### 3.4. `PUT /api/v1/work-plans/{planId}`

Переименовывает активный план текущего пользователя.

```json
{ "name": "Силовые тренировки" }
```

Ответ: `200 OK` с актуальным объектом. Если нормализованное название не изменилось, `updatedAt` и аудит не изменяются.

### 3.5. `POST /api/v1/work-plans/{planId}/archive`

Архивирует план текущего пользователя внутри активной родительской ветки. Ответ: `204 No Content`. Повторное архивирование собственного уже архивированного плана при активной ветке возвращает `204` без изменения времени и нового события истории. Если ветка архивирована, возвращается `404 NOT_FOUND`, в том числе при повторном запросе; чужой или отсутствующий план также даёт `404`. После F-6 endpoint архивирует также задачи плана, не меняя публичный контракт.

## 4. Изменение архивирования ветки

F-5 расширяет существующий endpoint `POST /api/v1/branches/{branchId}/archive` без изменения его публичного контракта: в одной транзакции он архивирует саму ветку и все её активные планы. Для ветки и каждого ранее активного плана устанавливается единый момент `archived_at` и `updated_at`; для каждого создаётся одно событие аудита. У уже архивированных планов `archived_at`, `updated_at` и аудит не меняются. Повторный вызов для собственной архивированной ветки остаётся `204` без новых изменений. При ошибке операции состояние ветки, планов и аудита откатывается.

Чтобы создание плана не прошло одновременно с архивированием ветки, все операции записи в планах (создание, переименование, архивирование) сначала берут блокировку строки родительской ветки, проверяют владельца и активность, а затем при необходимости блокируют строку плана. Архивирование ветки уже берёт эту блокировку в F-4 и после неё меняет планы; единый порядок «ветка → план» предотвращает гонку и взаимную блокировку. Для операции по `planId` сначала узнают `branchId`, затем после блокировки ветки повторно проверяют план и владельца. Простой внешний ключ на ветку не защищает от вставки активного плана под архивированной веткой.

Каскадное изменение планов выполняется наборной операцией по `branch_id` и `archived_at IS NULL` с получением ID фактически изменённых строк; события аудита записываются для этих ID в той же транзакции. Это исключает N+1 чтение планов и повторные события. Если используется bulk-обновление вне JPA persistence context, нельзя возвращать из него устаревшие entity.

В F-6 эта же транзакция будет расширена задачами. Восстановление добавляется F-9.

## 5. Правила обработки

1. Для `name` и `q` используется точный алгоритм [раздела 4 F-4](../F-4-branches/system-description.md): Unicode NFC, удаление определённых там краевых кодовых точек и подсчёт длины в кодовых точках Unicode. Для `name` допустимы 2–150, для `q` — 0–150; пустой `q` равен отсутствующему. Серверная валидация окончательна.
2. Список и чтение планов присоединяют родительскую ветку и проверяют `branches.user_id = verifiedUserId`, `branches.archived_at IS NULL` и `work_plans.archived_at IS NULL`. Операции записи дополнительно используют порядок блокировок из раздела 4. Прямое архивирование находит собственный план независимо от его `archived_at` для идемпотентного `204`, но только при активной ветке.
3. События плана пишутся в существующую `audit_events` с `entity_type = work_plan`, `entity_id = planId`, `user_id` владельца ветки и действиями `created`, `renamed`, `archived`. `changes` содержит затронутые поля с `from`/`to`: при создании — `branchId` и `name`, при переименовании — `name`, при архивировании — `archivedAt`. `occurred_at` совпадает с моментом изменения; при каскаде используется общий момент из раздела 4. Прямое и каскадное архивирование каждого активного плана дают ровно одно событие, уже архивированный план не даёт повторного. Изменение сущности и аудит коммитятся в одной транзакции; токены и подписи в аудит не попадают.
4. Пагинация — keyset по `(created_at, id)`. Сервис читает `limit + 1` записей, чтобы определить `nextCursor`.
5. Redis-кэш для пользовательских планов на этом этапе не вводится: запросы опираются на индекс и keyset-пагинацию; необходимость оптимизации подтверждается измерениями согласно NFR 3.2.

## 6. Безопасность и надёжность

- Gateway проверяет access JWT, а `tasks` принимает только подписанный внутренний контекст пользователя согласно F-4.
- Проверка владения выполняется на сервере для всех операций над веткой и планом.
- Архивирование плана и каскадное архивирование ветки транзакционны (NFR 4.3).
- Ошибки не раскрывают существование чужих или архивированных данных.
- Основные API должны отвечать не дольше 200 мс, списки — не дольше 500 мс (NFR 3.1).
