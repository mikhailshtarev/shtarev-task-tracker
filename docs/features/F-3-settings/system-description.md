# F-3. Персональные настройки и профиль — системное описание

## 1. Обзор

Системное описание фичи F-3. Бизнес-правила и критерии приёмки — в [business-description.md](business-description.md).

Принятые архитектурные решения (PM, 2026-09-12):

| Решение | Выбор |
| --- | --- |
| Размещение | Профиль и настройки живут в сервисе `auth` (users-домен). Таблица `users` и `GET /auth/me` уже принадлежат ему — отдельный микросервис ради CRUD настроек не создаётся |
| Доставка настроек другим сервисам | Auth — единственный владелец кэша настроек. Сервисы Tasks и Game получают настройки только через REST auth и не создают собственных Redis-копий |

## 2. Архитектура

```
┌──────────┐   PUT /auth/me        ┌─────────────────────────────┐
│ Frontend │   GET/PUT /auth/settings ──▶ Gateway ──▶ auth       │──▶ PostgreSQL (users, user_settings)
│          │                       │             │               │──▶ Redis (единый кэш настроек)
└──────────┘                       │             │               │
                                   │             ▼               │
┌──────────┐   GET /auth/settings ─┘     Tasks / Game          │
│ Сервисы  │ ──── (Bearer пользователя) ─────────────▶ auth ────┘
└──────────┘      без локального Redis-кэша
```

- Все новые эндпоинты размещаются в сервисе `auth` под basePath `/api/v1/auth` — Gateway уже маршрутизирует `/api/v1/auth/**` в этот сервис, новых правил маршрутизации не требуется.
- Валидация access token для новых эндпоинтов — как в F-2 (RS256, JWKS). Пользователь оперирует только своими данными: `userId` всегда берётся из `sub` токена, из тела запроса не принимается.
- Настройки применяются к уже созданным данным без миграций данных: время хранится в часах с точностью до 5 минут (F-6, F-12), единица оценки — параметр отображения.

## 3. Схема базы данных

Миграции `V2__add_user_settings.sql` и `V3__remove_game_base_exp.sql` (сервис `auth`):

```sql
CREATE TABLE user_settings (
    user_id           UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    estimation_unit   TEXT    NOT NULL DEFAULT 'hours'
                      CHECK (estimation_unit IN ('hours', 'pomodoros')),
    pomodoro_minutes  INT     NOT NULL DEFAULT 25
                      CHECK (pomodoro_minutes BETWEEN 5 AND 120 AND pomodoro_minutes % 5 = 0),
    game_mode_enabled BOOLEAN NOT NULL DEFAULT false,
    budget_hour_cost  INT     NOT NULL DEFAULT 5
                      CHECK (budget_hour_cost BETWEEN 1 AND 1000),
    created_at        TIMESTAMP NOT NULL DEFAULT now(),
    updated_at        TIMESTAMP NOT NULL DEFAULT now()
);
```

- `user_id` — первичный ключ (настройки 1:1 с пользователем), ссылка на `users.id`.
- Значения по умолчанию совпадают с разделом 6 бизнес-описания.
- Миграция `V3__remove_game_base_exp.sql` удаляет ранее добавленную колонку `game_base_exp`; базовый опыт за час фиксирован в игровой логике на уровне 5.
- Строка настроек создаётся при регистрации пользователя (оба потока F-2: email и Google) — в `AuthService.register` / Google-флоу, в одной транзакции с созданием `users`.
- Базовая награда игровой валюты (константа 5) в БД не хранится — она фиксирована в коде сервиса Game (F-13).
- Изменений таблицы `users` не требуется: колонка `name` создана в `V1`.

## 4. API-контракты

Формат ошибок — единый (NFR 15.2): `{ "error": { "code", "message", "details" } }`.

### 4.1. PUT `/api/v1/auth/me`

Обновление профиля. Требует Bearer token.

**Request body:**

```json
{ "name": "Иван" }
```

| Поле | Тип | Обязательность | Валидация |
| --- | --- | --- | --- |
| `name` | string \| null | Да | 0–100 символов; `null` или пустая строка — очистить имя |

**Responses:**

| HTTP | Условие | Тело |
| --- | --- | --- |
| `200 OK` | Профиль обновлён | `{ "id": "UUID", "email": "user@example.com", "name": "Иван" }` |
| `400 Bad Request` | Валидация | `VALIDATION_ERROR` с `details` |
| `401 Unauthorized` | Нет/недействителен Bearer | `UNAUTHORIZED` |

**Поведение:** обновляет `users.name` по `sub` токена и возвращает актуальный профиль. Данные пользователя из Google не затрагиваются — имя перекрывается значением из профиля (business-description, решение 2).

### 4.2. GET `/api/v1/auth/settings`

Настройки текущего пользователя. Требует Bearer token.

**Response `200 OK`:**

```json
{
  "estimationUnit": "hours",
  "pomodoroMinutes": 25,
  "gameModeEnabled": false,
  "budgetHourCost": 5
}
```

### 4.3. PUT `/api/v1/auth/settings`

Полное обновление настроек. Требует Bearer token.

**Request body:** та же структура, что и в ответе `GET` (все поля обязательны — полное обновление).

| Поле | Тип | Валидация |
| --- | --- | --- |
| `estimationUnit` | string | `'hours'` или `'pomodoros'` |
| `pomodoroMinutes` | int | 5–120, кратно 5 |
| `gameModeEnabled` | boolean | — |
| `budgetHourCost` | int | 1–1000 |

**Responses:**

| HTTP | Условие | Тело |
| --- | --- | --- |
| `200 OK` | Настройки обновлены | Актуальный объект настроек |
| `400 Bad Request` | Валидация | `VALIDATION_ERROR` с `details` (по одному на поле) |
| `401 Unauthorized` | Нет/недействителен Bearer | `UNAUTHORIZED` |

**Поведение:**

1. Валидирует все поля (серверная валидация обязательна, диапазоны — раздел 5 бизнес-описания).
2. Обновляет строку `user_settings` по `sub` токена.
3. Инвалидирует Redis-ключ `settings:{userId}` (см. раздел 5).
4. Возвращает актуальные настройки.

## 5. Доставка настроек другим сервисам

| Параметр | Значение |
| --- | --- |
| Способ | REST `GET /api/v1/auth/settings` с Bearer-токеном пользователя. Только auth читает и заполняет Redis-кэш; Tasks и Game не держат собственных копий |
| Кэш | Единый Redis-ключ `settings:{userId}`, владельцем которого является auth; TTL 15 минут |
| Инвалидация | После успешного коммита `PUT /auth/settings` auth удаляет единый ключ. Следующее чтение возвращает актуальные данные из PostgreSQL и заполняет кэш заново |
| Fallback | При недоступности Redis auth читает PostgreSQL напрямую. При недоступности auth сервисы не используют устаревшие настройки: зависящие от них асинхронные игровые начисления откладываются и повторяются после восстановления auth |

Единый кэш исключает рассинхрон между сервисами и не требует широковещательной инвалидации. Настройки применяются к следующим операциям сразу после коммита; операция, начавшаяся до изменения, может завершиться по прежнему значению.

## 6. Интеграции и влияние на другие фичи

| Фича | Точка интеграции |
| --- | --- |
| F-2 (auth) | Миграции `V2` и `V3`, создание дефолтных настроек при регистрации, `PUT /auth/me` рядом с существующим `GET /auth/me` |
| F-6 (Задачи) | Единица оценки — только отображение и ввод; хранение в часах с точностью 5 мин; чтение настроек через раздел 5 |
| F-12 (Привычки) | Аналогично F-6 |
| F-13 (Игровой режим) | Флаг `gameModeEnabled`, `budgetHourCost` (z); базовый опыт e = 5 и константа награды валюты = 5 в коде Game; коэффициенты k = 1 / 1,5 / 2 в коде Game |
| F-15 (Подписки) | Задел: `gameModeEnabled` — пользовательский флаг, тарифный гейтинг накладывается поверх него в F-15 |

## 7. Фронтенд

| Маршрут | Экран | Доступ |
| --- | --- | --- |
| `/profile` | Профиль: email (read-only), имя (редактируемое), ссылка на `/change-password` (F-2) | Авторизованные |
| `/settings` | Настройки: единица оценки + длительность помидора, игровой режим + z | Авторизованные |

- Оба маршрута за `ProtectedRoute` (F-2).
- После `PUT /auth/me` контекст обновляет `user.name` (AuthContext из F-2), имя сразу видно в шапке/меню.
- Клиентская валидация повторяет серверную (диапазоны, длина имени), ошибки `VALIDATION_ERROR.details` показываются под полями.
- Скрытие игровых элементов при `gameModeEnabled = false` выполняется на уровне фича-флагов в F-13; в F-3 сохраняется и отображается только значение флага.

## 8. Безопасность

- Оба PUT-эндпоинта требуют Bearer token; `userId` только из токена — подмена чужого профиля невозможна.
- Серверная валидация всех полей (диапазоны, enum) — клиентская валидация не является защитой.
- Rate limiting не требуется (аутентифицированные low-risk операции), но логирование изменений — да: `updated_at` в `user_settings`, изменение профиля и настроек попадает в аудит-лог (NFR 5.3).

## 9. Риски и заделы

| Пункт | Описание |
| --- | --- |
| Выделение users-сервиса | Если users-домен вырастет (экспорт данных F-19, подписки F-15), эндпоинты переносятся в отдельный сервис; Gateway-маршрутизация меняется, контракты сохраняются |
| Настройки округления помидоров | В БТ 4.6 сказано «по умолчанию округляет до целого» — задел под будущую настройку; сейчас фиксировано |
| Недоступность auth | Игровые начисления не выполняются по устаревшим настройкам: задача остаётся завершённой, а начисление откладывается и повторяется |
