# Проверка пользовательского access JWT на Gateway и в auth

## 1. Область действия

Для маршрутов к `tasks` и другим не-auth сервисам Gateway — единственная точка разбора и проверки **пользовательского access JWT**. После проверки он передаёт этим сервисам только минимальный подписанный контекст с `userId`; они не получают Bearer, не декодируют access JWT и не загружают JWKS. Каждый сервис по-прежнему проверяет владение своими ресурсами.

`auth` — исключение: Gateway маршрутизирует `/api/v1/auth/**` без повторной проверки access JWT и передаёт в `auth` пользовательский `Authorization`. `auth` самостоятельно разбирает и проверяет access JWT на своих защищённых endpoint'ах, а также refresh JWT из HttpOnly cookie, токены подтверждения и сброса пароля и Google ID token в соответствующих сценариях. Это сохраняет ответственность `auth` за собственные операции без двойной проверки одного JWT. Прямой публичный доступ к портам сервисов закрыт: клиент входит через Gateway.

Внутренние запросы сервис → сервис без Gateway не получают автоматически пользовательский контекст. Их авторизация определяется отдельно; нельзя принимать неподписанный `userId` или использовать пользовательский Bearer, которого нет у `tasks`.

## 2. Публичные и защищённые маршруты

Для `/api/v1/auth/**` Gateway применяет маршрутизацию и общие меры (CORS, rate limiting), но не валидирует access JWT. Публичные и защищённые методы определяет `auth` в `SecurityConfig`: `/me`, `/settings`, `/change-password` требуют действующий Bearer access JWT; login/register и остальные публичные операции работают по собственным правилам, а refresh/logout проверяют cookie и `Origin`. Gateway не должен ошибочно удалять `Authorization` или cookie из запроса к `auth`.

На защищённых маршрутах **к другим сервисам** Gateway принимает ровно один корректный Bearer, проверяет RS256-подпись по JWKS `auth`, `exp`, `nbf` (если есть), `iss`, `type = access` и UUID в `sub`. Отсутствующий, refresh или неверный access JWT даёт `401 UNAUTHORIZED` до вызова такого downstream. Gateway кэширует JWKS; декодирование и загрузка ключей не блокируют WebFlux event loop, неизвестный `kid` не даёт доступ без успешной проверки подписи. `auth` проверяет собственные токены своими ключами. Проверка `tokens_valid_from` и blacklist не выполняется при каждом access-запросе: срок access JWT — 15 минут.

CORS preflight (`OPTIONS` с `Origin` и `Access-Control-Request-Method`) обрабатывается Gateway до проверки Bearer: токен для preflight не требуется, запрос не направляется в downstream и внутренний контекст не создаётся. Разрешённые origin, методы и заголовки задаются CORS-конфигурацией Gateway; обычные защищённые запросы продолжают требовать access JWT.

Gateway удаляет **все** присланные клиентом заголовки с префиксом `X-Internal-` на любом маршруте. Для не-auth сервиса после проверки JWT он удаляет `Authorization` из исходящего запроса и создаёт новый внутренний контекст. Для `auth` он не создаёт внутренний пользовательский контекст и сохраняет `Authorization` и cookie без изменения.

## 3. Внутренний контекст Gateway → не-auth сервис

| Заголовок | Значение |
| --- | --- |
| `X-Internal-User-Id` | Канонический UUID из проверенного `sub`, нижний регистр |
| `X-Internal-Auth-Time` | Время подписи в секундах Unix, десятичное целое без пробелов |
| `X-Internal-Auth-Signature` | Base64URL без padding от HMAC-SHA256 |

Вход HMAC кодируется UTF-8 и имеет вид `v1\n<service-id>\n<userId>\n<timestamp>\n<METHOD>\n<raw-path>`. `service-id` — фиксированный идентификатор получателя (`tasks` и т. д.), не клиентский заголовок. `METHOD` — HTTP-метод в верхнем регистре; `raw-path` — путь без query string **после** всех переписываний Gateway, ровно в том виде, в каком его получает сервис. Query string и тело не входят в подпись: контекст удостоверяет пользователя и назначение запроса, а не заменяет TLS-защиту всего запроса.

У Gateway отдельный случайный HMAC-ключ для каждого не-auth сервиса; сервис знает только свой ключ. Ключ содержит не менее 32 байт, хранится в Base64-представлении в секретах окружения, не попадает в Git и логи, не совпадает с ключом подписи JWT. Отсутствующий или некорректный ключ запрещает запуск защищённого маршрута. Для ротации ключей допускается короткое окно проверки текущим и предыдущим ключом; Gateway подписывает только текущим. Для `auth` такой ключ не нужен.

Каждый не-auth сервис проверяет ровно одно значение каждого внутреннего заголовка, канонический UUID и timestamp (отклонение не более 30 секунд), пересчитывает HMAC со **своим** `service-id`, методом и полученным путём, сравнивает подпись в постоянное время и лишь затем создаёт локальный контекст пользователя. Отсутствующий, повторяющийся, поддельный или просроченный контекст даёт `401 UNAUTHORIZED` до контроллера. Заголовок `Authorization` от Gateway не используется как резервный источник личности. В контроллеры передаётся только проверенный `userId`, а не исходные заголовки.

Для защищённых маршрутов к не-auth сервисам публичный `401 UNAUTHORIZED` означает только отсутствие или недействительность пользовательского access JWT, обнаруженные Gateway до обращения к downstream. Если Gateway уже проверил JWT, но downstream вернул `401` из-за отсутствующего или неверного внутреннего контекста, Gateway не отдаёт его клиенту как `401`: возвращает `502 Bad Gateway` с `{ "error": { "code": "UPSTREAM_UNAVAILABLE", "message": "Сервис временно недоступен. Попробуйте позже", "details": null } }`. Причина внутреннего сбоя и correlation ID фиксируются в технических логах без токенов и подписей. Клиент не пытается обновить JWT и не завершает сессию из-за такого `502`. Прямой диагностический вызов downstream по-прежнему получает `401`.

Порты downstream не доступны из публичной сети; связь Gateway → сервис шифруется по NFR 5. Короткий срок подписи не предотвращает повтор запроса внутри окна при компрометации сети, поэтому обязательны TLS, сетевая изоляция и отсутствие логирования подписей. Сервис-сервис вызовы и фоновые задания не должны подделывать пользовательский контекст; для них определяются отдельные доверенные механизмы.

Если при проектировании F-6 окажется, что отдельным HTTP-операциям `tasks` нужны настройки пользователя, Gateway **может** получить их у `auth` с пользовательским Bearer и передать вместе с `userId`. Это не требование F-4: перечень операций и полей ещё не определён. В таком варианте настройки и их версия/время получения должны входить в проверяемую подпись, а запрос `auth` добавит зависимость по задержке и доступности; без расширения этого контракта `tasks` не доверяет заголовкам с настройками. Для фоновых операций без Gateway всё равно требуется отдельный сервисный доступ к настройкам.

## 4. Миграция существующих сервисов

1. Gateway: оставить маршруты `/api/v1/auth/**` без своей проверки JWT и с исходным `Authorization`, но удалять клиентские `X-Internal-*`. Для остальных защищённых маршрутов централизовать валидацию access JWT, удаление Bearer и выпуск подписанного контекста. Добавить `/api/v1/branches/**` к `tasks`.
2. `auth`: сохранить собственную проверку access JWT на защищённых endpoint'ах и refresh JWT/cookie, Google ID token и публичных одноразовых токенов на соответствующих операциях. Изменение способа аутентификации `auth` для F-4 не требуется.
3. `tasks` и будущие не-auth сервисы: реализовать проверку контекста со своим `service-id` и ключом. Не подключать парсер пользовательского access JWT или JWKS-клиент.

## 5. Проверки готовности

- На защищённых маршрутах к `tasks` и будущим не-auth сервисам корректный access JWT проходит через Gateway, а отсутствующий, неверный, просроченный и refresh JWT отклоняются им. В `auth` такие токены проверяет сам сервис; Gateway не дублирует проверку.
- На маршрутах `auth` Gateway сохраняет `Authorization` и cookie; защищённые операции проверяют access JWT в `auth`, refresh/logout — cookie и `Origin`.
- Поддельные и повторяющиеся `X-Internal-*` от клиента не проходят сквозь Gateway. Не-auth downstream не получает пользовательский Bearer или claims сверх `sub`.
- Прямой вызов защищённого endpoint'а `tasks` без подлинного контекста, с контекстом другого сервиса, изменёнными `userId`/временем/методом/путём или истёкшим timestamp получает `401`.
- После успешной проверки JWT ответ `401` от `tasks` преобразуется Gateway в публичный `502 UPSTREAM_UNAVAILABLE`; при этом ошибка не запускает обновление access JWT на клиенте.
- CORS preflight к защищённому маршруту проходит без Bearer и без вызова `tasks`; обычный запрос без Bearer получает `401`.
- Проверка владения ресурсом по `userId` остаётся в каждом сервисе; ошибки не раскрывают чужие данные.
